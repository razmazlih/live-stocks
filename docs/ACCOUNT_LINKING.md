# Guarded account merge service

The website and production ownership migration are live. Repeated sign-in with the same Google identity already returns the same account. **General merging of two existing portfolio profiles remains disabled**: `ACCOUNT_LINKING_ENABLED` is absent/false in production. The new server implementation is local-tested, not deployed or exercised against real users. It never enables password authentication.

A verified email match is a private suggestion, not permission. Ordinary Better Auth registration has a unique email and Google reuses the existing identity. The two-profile regression therefore uses two explicitly imported, case-variant synthetic identities; it does not claim ordinary signup creates duplicates.

## Browser and authorization flow

`GET /api/account/link/status` returns only `{available:false}` while disabled. When explicitly enabled, an actual verified SDK session and active canonical identity are required to discover opaque HMAC candidate handles. No raw subject, email, counts or balances appear before both proofs.

1. Same-origin `POST start` resolves the handle again for the caller, creates one durable SQL job, and sets a random HttpOnly, host-only, SameSite=Lax cookie scoped to `/api/account/link` (Secure on HTTPS). Only its SHA-256 digest is stored. Browser JSON/URLs never contain the capability secret.
2. `POST :id/reauth` binds a single-use challenge to the exact operation and step, then signs out the current SDK session. Its local sign-in return URL leads to `GET :id/callback`. The callback requires the exact expected subject, a live verified SDK session created after the challenge, a different session ID, and a fresh canonical identity. Both proofs expire after five minutes. Restarting the first proof clears both cached proofs.
3. Only after both proofs does the service call the SQL preview and read each profile's scoped counts/settings. A second SQL preview rejects changes during these reads. The public review exposes no credential ciphertext or value. Confirmation binds the exact pair, canonical target, version/hash, explicit settings/key choices and acknowledgment.
4. SQL freeze rechecks the manifest and proof versions under profile locks, drains existing writes, blocks both profiles, revokes widgets/MCP approvals and deletes all their live sessions atomically. A changed review returns `REVIEW_CHANGED` with a newly stored review; it never transfers the changed portfolio silently.
5. The worker reencrypts the chosen credential under the canonical profile's AES-GCM AAD, runs the existing transactional preservation RPC, revokes all participant/alias approvals, sessions and refresh/access-token rows, then supplies a receipt to the completion RPC. Both original encrypted credentials remain archived under their original AAD. Every position ID and its own FIFO lots remain distinct.
6. Completion requires a new login after the database cutoff; a successfully resolved fresh canonical session stops the completion redirect. Widgets/MCP stay disabled until explicitly reconnected.

All mutation routes check Origin and reject cross-site requests. Session/candidate assertions supplied by the browser are not accepted. The operation cookie only authorizes the exact existing job; it cannot create a different pair, choose an unreviewed owner or bypass dual proof and consent.

## Durable recovery

The ceremony uses prefixed rows in the existing private `livestocks_auth.verification` table. The limited backend role already has CRUD there and no financial grants. These rows use a distant storage expiry so SDK cleanup cannot erase a frozen operation; **the browser capability separately expires after 24 hours**. They contain proof metadata and review counts, never bearer tokens, passwords or plaintext market-data keys. The auth storage shape is unchanged. The separate `20261115140805_guarded_account_merge_creation.sql` migration adds only two service-only functions; it was separately reviewed and applied on 2026-11-15, along with the effective-function-ACL hardening migration. This does not enable the HTTP merge feature. The four production cutover migrations remain byte-for-byte unchanged.

A dedicated, bounded strict-TLS auth-role pool holds ceremony row locks; a separate auth pool performs revocation, avoiding nested checkout exhaustion. One outstanding intent per initiating canonical profile is enforced under an advisory lock. A row lock serializes each ceremony's requests. SQL stages commit independently and remain idempotent. A lost acknowledgment is resolved by reading the same durable job; failed preparation rolls back every financial change while retaining the earlier freeze. After preparation, retries never decrypt a source credential that has already moved. Failures remain `reconcile_required`; cancellation never unfreezes a committed job.

`/api/account/link/recovery` is an intentionally session-independent, cookie-authorized page with no financial data. It can resume the saved frozen job after the ordinary sessions have been revoked. GET does not advance the worker; same-origin POST does. This avoids relying on the login-protected Settings page for recovery. If the browser capability is lost or expires, the server worker can still complete an already frozen job. Expired unconfirmed jobs are cancelled and their participant locks released by the worker, without changing financial data. The creation intent is persisted before SQL creation, so an interrupted response cannot leave an undiscoverable job. Guarded creation and lookup share a request advisory lock and exact issuer/participant binding. An absent intent is abandoned only after the database confirms expiry; creation checks the same immutable expiry with `clock_timestamp()` after acquiring the lock, so a late request cannot resurrect it.

`POST /api/internal/account-merge-worker` accepts only an exact, at least 32-character `ACCOUNT_LINKING_WORKER_SECRET` bearer credential and a true feature flag. It scans at most 20 stored records with a 15-second between-job budget (hard maximum 20 seconds), accepts no job/owner/choice arguments, and cannot freeze an unconfirmed job. It may replay only an already persisted, authorized creation intent. Confirmed work is prioritized; all failed attempts advance queue timestamps so one failure does not repeatedly displace later records. Completed/cancelled records leave the queue. The response `{processed,pending,deferred}` is bounded progress, not a claim that every job completed; `deferred` can be a lower bound when more than 20 records remain. Individual database operations and service HTTP calls also have timeouts.

A free-tier daily fallback is defined in `vercel.json` at 04:00 UTC: `GET /api/internal/account-merge-cron` delegates to the same authenticated worker. Configure **the exact same private value** for `CRON_SECRET` and `ACCOUNT_LINKING_WORKER_SECRET`; the manual POST endpoint remains available. These secrets must not be public, committed, or written to command arguments/logs. The cron route is not an anonymous bypass. Confirmation runs the worker immediately and the user can resume with the cookie for 24 hours; the daily task is a fallback, not an instant completion guarantee. A growing backlog or repeated `pending` result requires a protected manual POST invocation and inspection of the durable job. After browser capability expiry, operator/cron recovery is required; do not extend the capability or reopen anonymous permissions.

Before enabling: verify the recorded helper/hardening migration versions and fingerprints, provision the matching private worker secrets, verify unauthorized cron/manual requests fail, verify the deployed daily schedule, then explicitly enable the feature. No new secrets or production flags were set by this local implementation. The sign-in screen now offers the cookie-authorized recovery entry independently of account/session bootstrap; the account review also exposes it before confirmation.

## Local verification and remaining release gates

Run from the repository with native PostgreSQL tools on PATH:

```sh
npx vitest run __tests__/account-linking-service.test.ts __tests__/account-linking-http.test.ts __tests__/account-linking-client.test.ts __tests__/account-linking-ui.test.tsx __tests__/account-merge-accounting.test.ts
PATH=/opt/homebrew/opt/postgresql@17/bin:$PATH python3 scripts/test-account-linking.py
```

The native runner creates a fresh loopback-only database, applies existing migrations, loads no `.env`, accepts no external URL, uses only synthetic data and removes its own cluster. It tests actual SDK-signed session cookies and limited backend storage, SQL service-role RPCs, stale-preview rejection, rollback after a complete transfer before commit, lost commit acknowledgment, restarted-worker recovery, all six exact financial row sets, timestamps/IDs/parents, fixed-time FIFO/portfolio totals, credential AAD/archive preservation, and approval/refresh revocation. It does not substitute mocked SQL for the transfer.

The native fixture's sessions are created through the SDK internal test adapter. **A real two-identity Google browser proof/consent/recovery ceremony is not yet verified.** No production general merge has run. Keep availability off until independent security review, browser tests including account switching/callback replay, the visible recovery entry point and the deployed bounded worker schedule are verified. Deployment/enabling is a separate action; no ownership rollback may restore anonymous access or delete retained financial history.
